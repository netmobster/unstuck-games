JUDGEMENT OS

a second opinion, with a receipt

A second opinion for your Claude Code skills, only when they need one.

You came for a skill. Sit down.

A skill makes its normal decision in code. When that code can tell the answer might depend on context, and only then, it asks two judges: a small model and a big one that know the person they're working for, each given the same bounded question. They advise; they can't act. If both disagree with real confidence, you settle it. Every path is logged, and any failure falls back to the code's own pick.

Judgement is an escalation, not the way the skill runs. When there's nothing to judge, the cost is two log lines.

Add it to your own skill

Eight steps, from the integration spec. The skill keeps its own rule; the Judgement OS brings the judges, the checks and the log.

Your skill provides the decision's id, the default pick in code, the consult-only-if rule in code, the bounded question, and how a disagreement reaches the person. The Judgement OS provides the judges, checks on every answer, the interrupt rule, the append-only log and its counts, the open, verdict, combine and close commands, and the results page.

Read the spec ↗

  1. 01
    The decision script.

    A script in your plugin that takes the decision's inputs and prints the default, whether to consult, why, and the question. Pure code, tested.

    { "default", "consult", "consultWhy", "question" }
  2. 02
    Find the Judgement OS.

    Installed plugins don't sit side by side, so a relative path won't reach. Not found: use the default and log nothing. The skill must work without it.

    node find-plugin.js labs scripts/record.js
  3. 03
    Open the call.

    Logs the pick and why the judges were or weren't asked. Every path logs this line.

    record.js open --decision <file> --run live --point <your.decision>
  4. 04
    Ask both judges, only if consult.

    Two agent calls in one message, one per model, the question word for word: one wait.

    subagent_type: "labs:second-opinion" · small + big
  5. 05
    Record each answer through a file. Never the shell.

    A heredoc ends early on an answer that contains a line saying EOF. An answer the recorder marks invalid counts as no answer.

    record.js verdict --call <id> --role small|big --file <answer>
  6. 06
    Combine, then settle.

    The recorder applies the interrupt rule. By default the person hears about it only when both judges disagree, each at medium or high confidence, and a judge past the timeout counts as no answer. What it shows becomes one question; everything else is silent.

    record.js combine --call <id>
  7. 07
    Close the call.

    What was used, and how it was settled: by the rule, by a name, by the person, by the picker, typed, or dismissed.

    record.js close --call <id> --final <used> --settled-by <how>
  8. 08
    Fail safe.

    Any failure in steps 2 to 7 falls back to the default and the skill carries on. Judgement never stops a skill.

    → the rule's pick

Security model

The judge is an untrusted advisor. What protects you is that it can't do anything.

Read onlyOne tool, one file. It reads; it never writes, sends or runs anything.
Checked in codeEvery answer is checked before anyone sees it: valid JSON, a confidence, a fact behind any non-proceed verdict, nothing from your private topics.
Never through a shellModel text travels by file. It is never pasted into a command.
Private topics stay outFiltered before the question is built, and an answer that touches them is thrown away.
No authorityNone over sending, deploying, writing your data, merging, or the guard rules. It recommends; a person settles.
Not yetCutting a slow judge off. A late answer no longer counts, but the skill still waits for it. Labelling context as data reduces injection; it doesn't prevent it.

JUDGEMENT OS*

A second opinion, only when your skills need one.

Your skills keep making their normal calls in code. When the code can tell an answer might depend on you, two judges who know how you work weigh in, and you hear about it only when both disagree.

What this is

  • A rule that decides, and two judges asked only when it can't tell.
  • One profile you write, and one bounded question. That's all a judge sees.
  • Every call logged, and counted.

What this isn't

  • An agent. The judges read; they never send, deploy, write or merge.
  • Memory. The judges know your profile, not your chat history.
  • Fast, yet. A judge takes 40 seconds or more.

Use this if

  • You build or run your own Claude Code skills.
  • Some of their steps are judgement calls that depend on who's at the keyboard.
  • You'd rather settle a real disagreement than have AI quietly overrule you.

Don't use this if

  • Your skills are all mechanical steps. There's nothing to judge.
  • You won't write a profile. Without one, no judge is ever asked.
  • You want AI to decide for you. It advises; you settle.

*No, really. Not actually an OS.

HOW IT WORKSJudgement is an escalation, not the way the skill runs.

A skill is a procedure. Most of its steps are mechanical. A few are judgement calls, where the right answer depends on who's at the keyboard and what's going on with them. Those steps get marked.

rule
Picks the default in code. Free, instant, the same answer every time. It also decides whether context could change it.
judges
Two of them, a small model and a big one, asked only when the rule's own test says context could change the answer. Each reads one profile file and one bounded question, and answers with a verdict and how sure it is.
you
Shown a disagreement only when both judges share it, each at medium or high confidence, as one question. A hunch, or one judge alone, never reaches you.
log
Every path: what the rule picked, why the judge was or wasn't asked, what it said, how it ended.

Any failure (no answer, a malformed answer, no labs plugin) means the rule's pick stands. When there's nothing to judge, the cost is two log lines.

  1. a skill step
  2. marked decision ── the rule picks
  3. could context change it?yes ↓no ──▶ the rule's pick
  4. two judges: one question
  5. both disagree, and mean it?yes ↓no ──▶ the rule's pick
  6. you decide
  7. the log ── every path

Each judge sees nothing the code didn't put in the question. It answers in one shape, and the recorder checks that shape in code before anything can show.

{"verdict":"proceed|clarify|challenge|redirect",
 "confidence":"low|medium|high",
 "why":"one sentence",
 "fact":"what it rests on",
 "suggestion":"the alternative, or null"}
proceed
The pick is fine. The right answer whenever context changes nothing.
clarify
It depends on something only you know. why is the question.
challenge
A different option fits better.
redirect
This decision is the wrong thing to be doing right now.

What reaches you

proceed · anything low · one judge alone
Nothing shown. Logged.
challenge · both, medium or high
One question: the suggestion (both, when the judges differ) or the default.
clarify · both, medium or high
The big judge's why is the question.
redirect · both, medium or high
“Do X instead?”, with both options.
invalid · or no answer
The default, silently.

The recorder checks every answer: valid JSON, a confidence, a fact behind any non-proceed verdict, nothing from your private topics. Anything else is logged as invalid and the rule's pick stands.

Five marked decisions are shown here; four ship in the General Edition. It's a pattern, not a single trick. In each one the rule's pick is the normal path and the judges are the escalation.

In all of them, no profile on the machine means the rule decides, and a request touching your private topics never reaches the judges.

“Instruction” means a model is asked to do it, and nothing checks that it did. We say which is which.

Held by code

  • The default pick, and when to ask.
  • Your private topics filtered out of the question.
  • The checks on every answer, the private topics included.
  • What reaches you: the recorder combines both answers under the interrupt rule and the timeout.
  • The log: its scripts write it, and the guard blocks direct edits.
  • The blind order in the LABS test kit, and the refusal of a second pick.

Held by instruction only

  • The judge reads only its one file.
  • Only what the recorder says to show is shown.
  • Answers never pass through a shell.
  • You settle every shown disagreement.
  • Both judges get the question, word for word.

Before a judge sits at a decision with consequences, rows move from the right column to the left. The red-team briefing has the full claims table and the attacks against it.

Not yet: cutting a slow judge off. A late answer doesn't count, but the skill still waits for it. Nothing here is bulletproof, and the page doesn't say it is.

The judges are tested like anything else, with a LABS test kit that runs in Jay's own install for now.

blind tries
Any morning, two models, labels hidden until you pick one.
recorded cases
Each case through both judges, every answer checked against what the case expects.
a results page
The log as a page. Every marked decision gets a row. Counts, never a score.

In the editions the log ships with the recorder, so your own counts build up as you use it: node labs-log.js summary prints them.

What the recorded cases found

  • 6 recorded test cases. On the one with nothing to judge, the rule stayed out. On the other 5, two different judge models answered.
  • Every judge answer watched so far took 40 seconds or more; three direct calls took 49 to 52.
  • 0 private topics reached a judge across the recorded cases.
  • 2 red-team reviews, both approving. Where the second said more than the code does, those claims are off this page.

The log counts agreement and overrides. That's all it measures. No accuracy scores, no percentages.
