JUDGEMENT OS

a second opinion, with a receipt

A second opinion for your Claude Code skills, only when they need one.

You came for a skill. Sit down.

A skill makes its normal decision in code. When that code can tell the answer might depend on context, and only then, it asks a judge: a model that knows the person it's working for, given one bounded question. The judge advises; it can't act. If it disagrees with real confidence, you settle it. Every path is logged, and any failure falls back to the code's own pick.

Judgement is an escalation, not the way the skill runs. When there's nothing to judge, the cost is two log lines.

Add it to your own skill

Eight steps, from the integration spec. The skill keeps its own rule; the Judgement OS brings the judge, the checks and the log.

Your skill provides the decision's id, the default pick in code, the consult-only-if rule in code, the bounded question, and how a disagreement reaches the person. The Judgement OS provides the judge, checks on every answer, the append-only log and its counts, the open, verdict and close commands, and the results page.

Read the spec ↗

  1. 01
    The decision script.

    A script in your plugin that takes the decision's inputs and prints the default, whether to consult, why, and the question. Pure code, tested.

    { "default", "consult", "consultWhy", "question" }
  2. 02
    Find the Judgement OS.

    Installed plugins don't sit side by side, so a relative path won't reach. Not found: use the default and log nothing. The skill must work without it.

    node find-plugin.js labs scripts/record.js
  3. 03
    Open the call.

    Logs the pick and why the judge was or wasn't asked. Every path logs this line.

    record.js open --decision <file> --run live --point <your.decision>
  4. 04
    Ask the judge, only if consult.

    One agent call, the question word for word.

    subagent_type: "labs:second-opinion"
  5. 05
    Record the answer through a file. Never the shell.

    A heredoc ends early on an answer that contains a line saying EOF. If the recorder prints invalid, the judge gave no answer: use the default.

    record.js verdict --call <id> --file <answer>
  6. 06
    Settle.

    Only a challenge, clarify or redirect at medium or high confidence reaches the person, as one question. Everything else is silent.

    medium | high → one question
  7. 07
    Close the call.

    What was used, and how it was settled: by the rule, by a name, by the person, by the picker, typed, or dismissed.

    record.js close --call <id> --final <used> --settled-by <how>
  8. 08
    Fail safe.

    Any failure in steps 2 to 7 falls back to the default and the skill carries on. Judgement never stops a skill.

    → the rule's pick

Security model

The judge is an untrusted advisor. What protects you is that it can't do anything.

Read onlyOne tool, one file. It reads; it never writes, sends or runs anything.
Checked in codeEvery answer is checked before anyone sees it: valid JSON, a confidence, a fact behind any non-proceed verdict, nothing from your private topics.
Never through a shellModel text travels by file. It is never pasted into a command.
Private topics stay outFiltered before the question is built, and an answer that touches them is thrown away.
No authorityNone over sending, deploying, writing your data, merging, or the guard rules. It recommends; a person settles.
Not yetA judge timeout. Until it ships, a slow judge makes the skill wait. Labelling context as data reduces injection; it doesn't prevent it.

HOW IT WORKSJudgement is an escalation, not the way the skill runs.

A skill is a procedure. Most of its steps are mechanical. A few are judgement calls, where the right answer depends on who's at the keyboard and what's going on with them. Those steps get marked.

rule
Picks the default in code. Free, instant, the same answer every time. It also decides whether context could change it.
judge
Asked only when the rule's own test says context could change the answer. It reads one profile file and one bounded question, and answers with a verdict and how sure it is.
you
Shown only a medium- or high-confidence disagreement, as one question. A hunch never reaches you.
log
Every path: what the rule picked, why the judge was or wasn't asked, what it said, how it ended.

Any failure (no answer, a malformed answer, no labs plugin) means the rule's pick stands. When there's nothing to judge, the cost is two log lines.

  1. a skill step
  2. marked decision ── the rule picks
  3. could context change it?yes ↓no ──▶ the rule's pick
  4. the judge: one question
  5. disagrees, and means it?yes ↓no ──▶ the rule's pick
  6. you decide
  7. the log ── every path

The judge sees nothing the code didn't put in the question. It answers in one shape, and the recorder checks that shape in code before anything can show.

{"verdict":"proceed|clarify|challenge|redirect",
 "confidence":"low|medium|high",
 "why":"one sentence",
 "fact":"what it rests on",
 "suggestion":"the alternative, or null"}
proceed
The pick is fine. The right answer whenever context changes nothing.
clarify
It depends on something only you know. why is the question.
challenge
A different option fits better.
redirect
This decision is the wrong thing to be doing right now.

What reaches you

proceed · or anything low
Nothing shown. Logged.
challenge · medium or high
One question: the suggestion or the default.
clarify · medium or high
The judge's why is the question.
redirect · medium or high
“Do X instead?”, with both options.
invalid · or no answer
The default, silently.

The recorder checks every answer: valid JSON, a confidence, a fact behind any non-proceed verdict, nothing from your private topics. Anything else is logged as invalid and the rule's pick stands.

Four marked decisions are built and installed. It's a pattern, not a single trick. In each one the rule's pick is the normal path and the judge is the escalation.

decisionthe rule's pickasks the judge when
a daily planning choice
The option used most in the last seven runs, ties to the most recent. When the rule is sure, the skill says what it picked in one line and keeps going.
It's late in the day, something is blocked and waiting on someone, or the handoff names a project the pick ignores.
which design system a page uses
A default style, a work style for work, a gaming style for gaming. A named style always wins.
A request reads as both work and gaming, or you say “judge it”.
which voice a draft is in
From where the draft is going: a newsletter, a pitch, a bit, a story. With nothing to go on, it asks you.
Two registers fit, or the draft reads differently from where it's going. The judge sees counts about the draft, never the draft.
which shape a page takes
Report, checklist, picker, explainer, one-pager or a multiple-choice report, from the request and how many decisions and steps the page carries.
Two shapes fit. When style and shape both need the judge, the two calls run in one message: one wait.

In the two newest decisions, no profile on the machine means the rule decides, and a request touching your private topics never reaches the judge. All four get this before release.

“Instruction” means a model is asked to do it, and nothing checks that it did. We say which is which.

Held by code

  • The default pick, and when to ask.
  • Your private topics filtered out of the question.
  • The checks on every answer, the private topics included.
  • The log: its scripts write it, and the guard blocks direct edits.
  • The blind order in /labs:try, and the refusal of a second pick.

Held by instruction only

  • The judge reads only its one file.
  • Low and proceed answers stay hidden.
  • Answers never pass through a shell.
  • You settle every shown disagreement.
  • A shadow judge never changes the outcome.

Before a judge sits at a decision with consequences, rows move from the right column to the left. The red-team briefing has the full claims table and the attacks against it.

Not yet: a judge timeout. A slow judge makes the skill wait. Nothing here is bulletproof, and the page doesn't say it is.

The judge is tested like anything else, and you can run the tests yourself.

What the recorded cases found

  • 6 recorded test cases. On the one with nothing to judge, the rule stayed out. On the other 5, two different judge models answered.
  • 12 real judge answers, each in 3 to 8 seconds.
  • 0 private topics reached a judge across the recorded cases.
  • 2 red-team reviews, both approving. Where the second said more than the code does, those claims are off this page.

The log counts agreement and overrides. That's all it measures. No accuracy scores, no percentages.

The judge is an agent, second-opinion, with one tool (Read) and one file to read. It answers in a fixed shape: a verdict, a confidence, why, the fact it rests on, and a suggestion. The recorder checks every answer in code before anything can show it. The log is append-only, and only its scripts write it.
